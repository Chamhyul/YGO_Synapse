# 직접 사용하며 검증하기

이 문서는 이전 네 파일 인덱스 방식의 기록입니다. 인벤토리 v2 및 DB 직접 조회 변경의 현재 확인 절차는 [INVENTORY_V2_ROLLOUT.md](INVENTORY_V2_ROLLOUT.md)를 사용합니다. 아래의 과거 테스트 통과 기록은 새 변경의 검증 결과가 아닙니다.

사용자가 로컬 화면으로 검증한 뒤 GitHub를 통해 배포합니다. 에이전트는 자동 테스트, 커밋, 푸시, 배포를 실행하지 않습니다.

## 수집 직후 파일 생성

1. 수정된 백엔드 코드가 반영되도록 로컬 Functions를 다시 시작하고, 로컬 사이트에서 새 카드가 포함된 팩을 수집합니다. Hosting뿐 아니라 Functions·Firestore·Storage도 로컬 환경에 연결되어 있어야 합니다.
2. 수집 완료 응답 시 Storage 화면에서 다음 파일의 생성 또는 갱신 시각을 확인합니다.
   - `public/indexes/idx_byName.json`
   - `public/indexes/idx_byNumber.json`
   - `public/indexes/idx_cid.json`
   - `public/cardNames.json`
3. 별도의 전체 재생성이나 ready 설정 없이 처음부터 파일을 만들 수 있어야 합니다. 파일에는 대기 기록이 있는 카드가 반영됩니다.
4. 방금 수집한 카드의 이름과 번호로 검색합니다. 목록 캐시는 최대 1분 간격으로 재확인하므로 화면을 새로 고쳐 확인할 수 있습니다.

팩 수집은 해당 요청의 수집 묶음이 끝난 직후 첫 100개를 직접 처리하며 파일 저장을 기다립니다. 이미 다른 인덱스 작업이 실행 중이라면 변경 기록을 남겨 그 작업 또는 후속 작업이 처리합니다. 정상적인 최초 실행은 스케줄러나 Tasks의 시작을 기다리지 않습니다.

## 남은 분량과 동시 수집

- 100개를 넘는 대기 기록이나 첫 처리 도중 추가된 기록은 후속 Tasks 실행이 처리합니다. 로컬 후속 처리에는 Tasks 에뮬레이터(기본 포트 9499)도 필요합니다.
- 다른 탭에서 수집을 추가했을 때 누락 없이 반영되고, 마지막에는 `system/cardIndexDispatch.status`가 idle로 바뀌는지 확인합니다.
- 파일 저장에 실패하면 수집 요청이 오류를 반환하고 대기 기록은 남아야 합니다. 일부 원본 카드 저장은 이미 성공했을 수 있습니다. 다음 수집 완료 시 남은 기록을 다시 처리합니다.
- 5분 주기 함수는 비정상 종료나 후속 예약 실패의 복구용입니다. 로컬에서 자동 실행된다고 가정하지 않습니다. 비정상 종료된 실행은 최대 15분의 잠금 만료까지 지연될 수 있습니다.

## 과거 자료 복구와 배포

이번 수정 전부터 존재한 카드 중 대기 기록이 없는 카드는 일반 증분 처리만으로 새 파일에 들어가지 않습니다. 이 경우에만 관리자 전체 재생성을 사용해 원본 `cards` 전체에서 복원합니다. 정상 수집을 시작하기 위한 필수 단계는 아닙니다.

전체 재생성은 `POST /rebuildAllCardIndexes`이며 사용자 ID 토큰과 관리자 권한이 필요합니다. 성공 200, 다른 작업 진행 중 409, 권한 없음 403, 처리 실패 500을 반환합니다. 실패 시 대기 기록을 보존하며 ready 값으로 일반 처리를 차단하지 않습니다. 손상된 JSON이나 과거 누락을 복구할 때 재실행합니다. 원본 카드는 삭제하지 않습니다.

사용자 로컬 검증 후 GitHub 배포가 완료되면 파일 갱신, 검색, 닉네임 변경을 다시 확인합니다. 기존 호환 별칭 제거는 전환 확인 뒤 별도로 진행합니다.

## 현재 검증의 한계

이번 직접 실행 변경은 자동 테스트와 실제 실행을 하지 않았습니다. 기존 테스트의 준비 상태 차단 항목은 최초 파일 생성 동작에 맞게 수정했습니다.

네 JSON 파일은 각각 저장되므로 동시에 전환되지는 않습니다. 중간 실패 시 대기 기록을 유지해 재처리합니다. Storage 에뮬레이터는 업로드의 `ifGenerationMatch`를 구현하지 않아 운영 환경의 파일 버전 충돌까지 확인할 수는 없습니다.

기존 `getRamMemoryStats`의 미정의 워밍업 변수/함수 참조는 이번 수정 범위에 포함하지 않았습니다.

## 레어도 저장 보호 확인

- 로컬 백엔드를 다시 시작하고 새 레어도가 포함된 카드나 팩을 수집합니다. Storage의 public/rarityMapping.json에서 기존 항목과 새 항목이 함께 남는지 확인합니다.
- 같은 자료를 다시 수집할 때 중복 항목이 생기지 않는지 확인합니다. 캐시로 수집을 건너뛰었다면 저장 경로를 검증한 것은 아닙니다.
- 서로 다른 새 레어도의 수집을 두 탭에서 진행해 두 항목 모두 남는지 확인합니다. 실제 저장 시점이 겹치지 않을 수 있어 이것만으로 충돌 재시도까지 검증되지는 않습니다.
- 실패 로그는 [RarityMapping]으로 구분됩니다. 카드 원본 저장이 성공해도 레어도 갱신은 실패할 수 있습니다. 실패한 레어도는 실제 재수집 등으로 다시 전달되어야 재시도됩니다.
- 캐시 정책은 유지하므로 화면 표시가 즉시 바뀌지 않을 수 있습니다. 저장 결과는 Storage 파일을 기준으로 확인합니다.
- Storage 에뮬레이터는 ifGenerationMatch 조건을 구현하지 않으므로 운영의 파일 버전 충돌 방어까지 검증할 수 없습니다.
- 이번 변경은 코드 읽기로 검토했으며 자동 테스트와 배포는 실행하지 않았습니다.

## 사용자 요청에 따른 자동 검증 결과 (2026-09-03)

사용자의 추가 자동 검증 요청에 따라 실행했습니다. 기존 15개와 새 레어도 저장 테스트 9개, 총 24개가 통과했습니다. 동시 변경 병합, 최초 생성, 중복 방지, 읽기·JSON 오류 시 보존, 충돌 재시도 상한, 저장 권한 오류를 격리된 Storage 대역으로 확인했습니다. cardService.js, cardScraper.js, integration.js, public/script.js의 구문 검사도 통과했습니다.

실행 환경은 로컬 Node.js 25.6.0이며 프로젝트 지정 버전은 24입니다. 실제 Node.js 24 배포 환경, 운영 Storage 충돌, 실제 크롤링 및 화면 동작은 이번 검증에 포함하지 않았습니다. 운영 데이터 접근이나 배포는 수행하지 않았습니다. 테스트 파일은 functions/test/rarityMapping.test.js에 추가했습니다.
