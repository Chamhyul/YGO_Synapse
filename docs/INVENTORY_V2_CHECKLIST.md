# 인벤토리 v2 / DB 검색 확인 체크리스트

아래 실제 환경 확인 항목은 미확인 상태입니다. 실행 후 통과한 항목만 체크합니다. 먼저 1~5를 확인하고, 6은 로컬 사본에서 예외 상황을 재현합니다.

2026-09-03 코드 점검: 격리 테스트 29개, JavaScript 구문 검사, `git diff --check`가 통과했습니다(Node.js 25.6.0). 늦은 CID 응답의 화면 덮어쓰기와 이관 실패 응답·계정 전환 시 재시도 처리를 수정하고 회귀 테스트 3개를 추가했습니다. 이는 브라우저·에뮬레이터·운영 환경 확인을 대신하지 않습니다.

## 1. 실행 준비와 FieldPath 오류

- [ ] 로컬 Functions를 재시작하고 사이트를 새로고침했다.
- [ ] 브라우저 Console·Network와 Functions 로그를 열었다.
- [ ] Firestore·Storage·Functions가 의도한 로컬 환경에 연결되어 있다.
- [ ] 관리자 인증으로 `POST /rebuildCardNames`를 실행했고, 200 응답과 `success: true`를 받았다. 다른 작업 진행 중인 409는 완료가 아니므로 종료 후 다시 확인한다.
- [ ] 목록 생성 로그에서 `FieldPath` 또는 `documentId` 오류가 다시 발생하지 않는다.
- [ ] Storage의 `public/cardNames.json` 갱신 시각이 바뀌고 이름·번호 배열이 정상적으로 들어 있다.
- [ ] 기존 오류를 일으켰던 카드 번호를 검색하면 이름·번호·레어도가 표시된다.

같은 번호를 다시 검색하는 것만으로는 목록 재생성 경로가 실행되지 않을 수 있습니다. 오류 수정 확인에는 목록 재생성 성공 여부를 포함합니다. 기존 원본 카드와 갱신 대기 기록은 지우지 않습니다.

## 2. 인벤토리 v1 → v2

- [ ] 로컬 v1 인벤토리 사본의 전체 수량과 번호별 수량·위치를 기록했다.
- [ ] 보유카드 목록을 로드하면 별도 이관 버튼 없이 CID 확보가 시작된다.
- [ ] 처리 완료 후 서버 인벤토리의 `version`이 `2`가 된다.
- [ ] 각 번호 항목에 `cid`와 `cidCheckedAt`이 저장된다. CID는 해당 `cards` 문서 ID와 같다.
- [ ] 같은 카드의 한국어·일본어·영어 수록 번호에는 동일한 CID가 저장된다.
- [ ] 이관 전후 이름·번호·레어도·일러스트·위치·수량·전체 집계가 동일하다.
- [ ] `getUserData` 응답의 `allCards`는 `[이름, 번호, 레어도, 수량, 위치, 일러스트, CID]`이며 화면에 불필요한 CID 열이 나타나지 않는다.
- [ ] `inventoryMigration.status`가 `complete`이고 `pendingCount`가 `0`이다. `unresolvedCount`가 있으면 해당 항목을 따로 기록한다.
- [ ] CID가 모두 확인된 v2를 다시 로드할 때, 이관용 이름·번호 DB 조회가 반복되지 않는다. 일반 상세 검색 조회와 구분한다.

`version: 2`는 새 저장 형식이라는 뜻입니다. 조회 결과가 미발견인 `cid: null` 항목이 남아 있어도 v2일 수 있습니다.

## 3. 카드 등록과 반복 검색

- [ ] 등록 화면에서 이름 일부·초성을 입력하면 기존 자동완성 후보가 표시된다.
- [ ] 이름을 확정하면 번호 목록·레어도·일러스트 선택이 정상적으로 채워진다.
- [ ] 다른 입력 행에서 같은 이름을 60초 이내 다시 조회하면 `searchCardByName` 요청 없이 결과가 표시된다.
- [ ] 이름 조회 후 번호 선택을 바꾸면 해당 번호의 레어도가 즉시 표시된다.
- [ ] 번호부터 입력해도 올바른 언어의 이름과 번호 목록이 표시된다.
- [ ] 새 카드를 등록하면 서버 인벤토리와 `updatedItems` 응답에 CID가 포함된다.
- [ ] 이동·차감 후 CID가 유지되고 수량·위치가 올바르게 반영된다.
- [ ] 모바일/데스크톱 전환 및 입력 행 복제·복원 후 번호 목록과 레어도 선택이 유지된다.
- [ ] 기존 6열 시트/데이터 이관이 가능하고 서버에서 CID가 보완된다.

## 4. 다국어 보유카드 검색

- [ ] 한국어 이름으로 검색하면 같은 CID의 일본어·영어 보유카드도 함께 나온다.
- [ ] 수록 번호로 검색해도 같은 CID의 다른 언어·번호 보유 내역을 함께 찾는다.
- [ ] 보유 항목을 눌렀을 때 저장된 CID로 올바른 상세 화면이 열린다.
- [ ] 다른 CID의 카드가 섞이지 않고 보유 수량이 중복 합산되지 않는다.
- [ ] 부분 일치·초성 검색은 로컬 결과를 먼저 표시하고 다른 언어 결과를 후속으로 보완한다.
- [ ] 후보가 40개를 넘으면 “다른 언어의 보유카드 더 찾기”로 나머지를 확인할 수 있다.
- [ ] 검색 중 다른 카드로 이동해도 이전 요청 결과가 새 화면을 덮어쓰지 않는다.
- [ ] CID가 아직 없는 항목도 이름·번호 일치 검색에서는 사라지지 않는다.
- [ ] 공식 카드 링크와 CID가 포함된 URL의 화면 복원이 정상이다.

처음 검색하는 외국어 이름은 DB에서 CID를 확인하는 시간이 필요합니다. 이미 확인한 이름·번호와 저장된 CID의 재고 검색은 로컬 데이터를 재사용합니다.

## 5. cardNames 유지와 인덱스 제거

- [ ] `cardNames.json` 파일 경로와 `{ names, numbers, updatedAt }` 형식이 유지된다.
- [ ] 새 클라이언트의 `getInitialData` 요청에 `inventorySchema: 2`가 포함된다.
- [ ] 새 클라이언트는 전체 `cids` 응답 없이 자동완성·등록·보유 검색을 수행한다.
- [ ] 로컬 사본에서 기존 세 idx JSON을 사용할 수 없게 해도 카드 검색과 목록 재생성이 동작한다.
- [ ] 새 카드 수집 후 `cardNames.json`에 이름·번호가 반영된다.
- [ ] 처리한 갱신 대기 기록은 정리되고, 작업 도중 새로 생긴 변경은 후속 처리된다.
- [ ] 기존 JP→KR 번호 보정과 필요한 번호 이관 경로에서도 `documentId` 오류가 없다. 번호 이관을 확인하려면 로컬 사본에서 실행한다.

운영의 구형 JSON 파일 삭제는 배포 확인 후 별도로 진행합니다.

## 6. 예외·동시 작업: 로컬 사본에서 확인

- [ ] 40개가 넘는 v1 인벤토리는 보유 목록을 표시한 뒤 후속 요청으로 처리를 끝낸다.
- [ ] 이관 도중 새로고침하거나 탭을 나갔다 돌아와도 저장한 진행 상태에서 이어간다.
- [ ] DB에 없는 번호는 `cid: null`로 남으며 원래 보유 내역이 보존된다.
- [ ] 번호와 이름이 서로 다른 카드를 가리키면 잘못된 CID를 확정하지 않는다.
- [ ] 일시적인 DB 오류는 `retryableError`로 표시되고 이후 재시도한다. 미발견으로 잘못 확정하지 않는다.
- [ ] 미확정 카드가 DB에 생긴 뒤 `cidCheckedAt`을 로컬에서 24시간 이전으로 설정하고 로드하면 CID가 보완된다.
- [ ] 이관 중 다른 탭에서 수량을 추가·이동·차감해도 최신 수량과 위치가 보존된다.
- [ ] 이관 중 삭제한 카드가 후속 저장으로 되살아나지 않는다.
- [ ] 계정을 바꾸면 이전 계정의 이관 후속 응답이 새 계정 인벤토리에 적용되지 않는다.
- [ ] 구형 클라이언트의 CID 없는 등록 요청도 새 서버에서 CID를 확보한다.

Storage 에뮬레이터만으로는 운영의 generation 충돌을 완전히 확인하기 어려울 수 있습니다. 동시 작업 확인 결과와 이 한계를 구분해 기록합니다.
