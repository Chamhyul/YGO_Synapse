# DB 직접 조회 및 인벤토리 v2 전환 계획

작성일: 2026-09-03

상태: 사용자 승인 후 코드 반영. 실행 검증·운영 배포 전입니다. 이전 `cidIndex.json` 신설 계획을 대체합니다.

구현한 기본값과 사용자 확인 절차는 [INVENTORY_V2_ROLLOUT.md](INVENTORY_V2_ROLLOUT.md)에 기록합니다. 아래 내용은 승인한 설계이며 운영 이관 완료를 뜻하지 않습니다.

## 1. 확정 방향

1. 서버 검색용 `idx_byName.json`, `idx_byNumber.json`, `idx_cid.json`을 제거하고 카드 원본 DB 조회와 검색 결과 캐시로 대체합니다.
2. `cardNames.json`의 이름·번호 목록 형식과 자동완성 역할을 유지합니다.
3. 인벤토리에 CID를 저장하고 `version`을 2로 올립니다. v1 인벤토리는 로드할 때 CID를 자동 확보하여 v2로 전환합니다.
4. 검색어로 찾은 CID를 기준으로 로컬 인벤토리를 검색하여 언어·수록 번호가 다른 동일 카드의 보유 내역을 모읍니다.

운영 카드 문서의 `names`·`numbers`는 모두 정상이라는 사용자 확인을 전제로 합니다. 카드 원본 필드의 전체 마이그레이션은 다시 하지 않습니다.

계획 승인 후 코드 구현까지 진행했습니다. 운영 데이터 변경·배포는 실행하지 않았습니다.

## 2. 현재 저장 구조와 v2 스키마

저장 위치는 Firebase Storage의 `users/{uid}/inventory.json`입니다. 수록 번호를 키로 사용하는 구조를 유지합니다.

아래는 변경 후의 가상 데이터입니다.

```json
{
  "version": 2,
  "updatedAt": "2026-09-03T00:00:00.000Z",
  "amount": 4,
  "locations": {
    "바인더": ["TEST-KR001"],
    "박스": ["TEST-JP001"]
  },
  "rarities": { "UR": 3, "SR": 1 },
  "cards": {
    "TEST-KR001": {
      "cid": "12345",
      "name": "한국어 카드명",
      "items": [
        { "rarity": "UR", "qty": 3, "loc": "바인더", "illustration": "1" }
      ]
    },
    "TEST-JP001": {
      "cid": "12345",
      "name": "日本語カード名",
      "items": [
        { "rarity": "SR", "qty": 1, "loc": "박스", "illustration": "1" }
      ]
    }
  }
}
```

- CID는 `name`과 같은 위치에 저장합니다. 동일 번호의 각 `items`에 반복 저장하지 않습니다.
- CID 값은 `cards` 문서 ID 문자열입니다. 확인하지 못한 경우 `null`을 사용하며 임의 값이나 `LOCAL_CID`를 저장하지 않습니다.
- v2는 CID 필드를 지원하는 저장 형식을 뜻합니다. 미확정 `cid: null`이 존재할 수 있으며, 모든 카드의 연결 완료 여부와 스키마 버전을 구분합니다.
- 기존 카드 이름·수록 번호·레어도·위치·일러스트·수량과 집계는 CID 이관만으로 변경하지 않습니다.
- 새 빈 인벤토리는 처음부터 `version: 2`로 생성합니다.

## 3. v1 로드 시 자동 전환

### 진입점

`getUserData`에서 인벤토리를 읽은 뒤, 응답으로 변환하기 전에 공통 `ensureInventoryV2` 서비스를 호출합니다. 추가·이동·차감·시트/데이터 이관 경로도 같은 버전 보장 및 CID 확보 규칙을 사용하여, 사용자 조회보다 쓰기가 먼저 발생해도 v1으로 되돌아가지 않게 합니다.

저수준 Storage 읽기와 DB 조회·이관 서비스를 분리하여 숨은 재귀 호출을 피합니다. 버전이 없는 기존 데이터는 v1으로 취급하고, 지원하지 않는 미래 버전은 자동으로 덮어쓰지 않습니다.

### 처리 순서

1. 원본 인벤토리와 정확히 같은 Storage generation을 함께 읽습니다.
2. CID가 없는 수록 번호를 중복 제거하고 DB `numbers` 배열로 조회합니다. 여러 항목을 묶어서 처리하고 동시 요청 수에 상한을 둡니다.
3. 유일한 카드가 확인되면 문서 ID를 CID로 사용합니다. 같은 번호가 여러 카드와 일치하면 저장된 이름으로 후보를 좁힙니다.
4. 번호로 못 찾는 항목은 이름으로 보조 조회합니다. 유일하고 일관된 결과만 채택하고, 번호와 이름이 다른 카드를 가리키면 미확정으로 남깁니다.
5. 일치 없음·복수 후보는 `cid: null`로 기록합니다. 통신·권한·DB 오류는 미발견과 구분합니다.
6. 처리한 항목의 CID만 원본에 반영하고 조건부 저장합니다. 처리 도중 모든 수량·보관 위치를 그대로 보존합니다.
7. 전체 항목에 대해 조회 결과가 확정되었을 때 `version: 2`를 저장합니다. 정상적인 조회의 미발견은 결과 확정에 포함하되 일시적인 오류는 포함하지 않습니다.
8. 성공한 저장 결과를 기준으로 클라이언트에 응답합니다. 저장하지 못했는데 전환이 완료됐다고 응답하지 않습니다.

### 큰 인벤토리와 미완료 처리

- 한 요청의 조회량과 실행 시간에 상한을 두고 묶음 단위로 CID 확보 결과를 저장합니다.
- 부분 처리 상태는 `version: 1`을 유지합니다. 이미 확인한 CID와 `null` 결과를 구분해 저장하여 다음 실행에서 같은 작업을 처음부터 반복하지 않습니다.
- 응답에 `inventoryMigration` 상태(`pending`, `complete`, `retryableError`)와 남은 처리 수·미확정 수를 포함합니다.
- 미완료여도 보유 내역은 먼저 표시합니다. 클라이언트는 제한된 간격으로 후속 처리를 요청하고, 완료 시 중단합니다. 화면을 떠났다가 다시 로드해도 저장한 진행 상태에서 이어집니다.
- 일시적 실패 시 간격을 늘려 재시도합니다. 반복 오류 때문에 재고 사용을 차단하거나 무한히 즉시 요청하지 않습니다.
- v2의 `cid: null` 항목은 이후 로드에서 일정 간격으로 재조회합니다. 이관 메타데이터의 재시도 시각을 사용해 매 로드마다 전체 미확정 목록을 읽지 않게 합니다.
- CID 확보를 위해 자동 크롤링을 실행하지 않습니다. 미확정 항목은 기존 이름·번호 검색으로 계속 사용할 수 있습니다.

### 동시 수정 보호

현재 `downloadInventory`는 메타데이터를 확인한 뒤 버전을 지정하지 않고 본문을 읽으며, 일부 경로의 `uploadInventory`는 무조건 덮어씁니다. v2 자동 이관과 수량 변경이 겹칠 때 데이터가 유실되지 않도록 이관 관련 전체 쓰기 경로를 조건부 갱신으로 통일합니다.

- generation을 문자열로 유지하고, 그 generation의 본문을 읽습니다.
- DB 조회는 오래 걸릴 수 있으므로 Storage 조건부 저장으로 최종 충돌을 검사합니다.
- 충돌 시 최신 인벤토리를 다시 읽고, 번호·이름이 그대로인 항목에만 확인한 CID를 재적용합니다. 바뀐 항목은 다시 확인합니다.
- 삭제된 카드를 되살리거나 이전 `items`·수량으로 덮어쓰지 않습니다.
- 저장 시점의 최신 전체 카드가 처리됐는지 다시 확인하고 버전을 올립니다. 동시에 추가된 미처리 카드를 놓치지 않습니다.
- 추가·이동·차감의 업무 변경을 재시도할 때는 매번 최신 상태에서 한 번 적용합니다. 이관 때문에 수량을 두 번 더하거나 빼지 않습니다.
- 기존 이관 및 `getUserData`의 형식 교정 저장도 같은 보호 경로로 옮깁니다.

## 4. 신규 등록·이관·클라이언트 계약

### 신규 카드 저장

- 이름·번호 검색 응답에서 얻은 CID를 등록 요청에 포함합니다.
- 서버는 번호와 CID의 연결을 카드 문서 또는 검증된 서버 캐시로 확인합니다. 클라이언트가 보낸 임의 CID를 그대로 확정하지 않습니다.
- 구형 클라이언트처럼 CID 없이 요청하면 서버가 번호·이름으로 확보합니다.
- 이동·차감은 저장된 CID를 그대로 유지하고, 변경 응답에도 포함합니다.
- 시트/데이터 이관은 기존 6열 입력을 계속 허용하고 서버가 번호별 CID를 보완합니다. 시트에 새 열을 강제하지 않습니다.

### 클라이언트 배열과 부분 갱신

기존 배열의 위치를 바꾸지 않고 마지막에 CID를 추가합니다.

```js
// 기존
[이름, 번호, 레어도, 수량, 위치, 일러스트]

// 변경
[이름, 번호, 레어도, 수량, 위치, 일러스트, CID]
```

- `getUserData`의 `allCards`, 추가·이동·차감의 `updatedItems`, 프론트엔드 `_inventory`와 저장 캐시에 CID를 전달합니다.
- 기존 행 갱신 시 수량뿐 아니라 새로 확보한 CID도 갱신합니다.
- 구형 6열 데이터는 CID 미확정으로 허용합니다. 내보내기·복제·붙여넣기·모바일/데스크톱 입력 상태 복원에서 7번째 값이 유실되거나 사용자가 보는 일반 열로 노출되지 않게 호출부를 점검합니다.
- 추가·이동·차감 후와 v2 이관 응답 수신 후 CID별 보유 재고 조회표를 재구성합니다.

## 5. DB 직접 조회와 검색 결과 캐시

### 서버

- 이름은 `names array-contains`, 번호는 `numbers array-contains`, CID는 문서 직접 읽기로 처리합니다.
- 조회에서 이미 받은 문서를 보관하고 CID 확보 후 같은 문서를 다시 읽지 않습니다.
- `searchCardByName`, `searchCardByNo`, `getCardMetadata`, `searchCard`가 같은 조회·캐시 계층을 사용하도록 정리합니다.
- 서버 캐시는 CID별 문서와 이름·번호 별칭을 관리하고, 수집·문서 갱신 시 관련 항목을 무효화합니다.
- 여러 후보 조회는 중복을 제거하고 제한된 병렬/배치 처리를 사용합니다. 조회 실패를 카드 미발견으로 간주해 수집하지 않습니다.
- 기존 인덱스 전용 응답 분기를 제거합니다. 번호 목록·레어도·일러스트·링크는 조회한 원본 문서에서 구성합니다.
- 응답 포맷터는 입력한 이름·번호의 언어를 고려합니다. 다른 언어의 번호가 기존 등록 목록에 무조건 섞이는 변경을 피합니다.
- 번호 보정과 데이터 이관의 `getIdxByNumber` 의존도 같은 DB 조회로 교체합니다.

### 클라이언트

- 등록 페이지에 명시적인 이름·번호별 검색 결과 캐시를 추가하여 새 입력 행에서도 이전 응답을 재사용합니다.
- 같은 검색에 대한 진행 중 요청을 공유합니다. 유효 기간은 기존 60초 검색 응답 캐시를 초기 기준으로 삼고, 직접 수집·갱신한 결과는 교체합니다.
- 현재 `dataset.cardData`, 드롭다운 옵션, 화면 복원과 HTTP 응답 캐시를 통한 재사용 동작을 유지합니다.
- CID 기준 상세 문서 캐시를 통합하되, 종류·스탯만 받은 부분 응답을 완전한 상세 문서로 오인하지 않습니다.
- 전역 `_nameToCid`·`_rawCidIndex` 의존을 제거하고 검색 응답·인벤토리·이미 조회한 카드의 별칭 캐시로 대체합니다.
- 공식 링크와 CID URL 복원도 저장된 CID 또는 DB 응답을 사용합니다.

## 6. 다국어 보유카드 검색

정확한 이름 또는 번호를 확정한 경우:

1. 로컬에 이미 확인한 이름·번호→CID가 있으면 재사용합니다.
2. 없으면 DB 검색으로 CID와 문서를 얻습니다.
3. 로컬 인벤토리에서 같은 CID의 모든 보유 행을 모읍니다.
4. 언어별 이름·수록 번호·레어도·위치는 유지하고 수량을 합산합니다.

보유 항목을 직접 클릭하면 해당 항목의 CID를 사용하므로 이름→CID 조회를 생략할 수 있습니다. CID 미확정 항목은 기존 이름·번호 일치 검색으로 표시합니다.

부분 일치·초성 포괄 검색은 별도로 처리합니다. 먼저 기존 `cardNames.json` 목록과 보유 이름을 로컬 검색하여 결과를 표시합니다. 다른 언어의 미조회 후보까지 확장하려면 후보 이름들의 CID를 서버에서 묶어서 조회하고 보유 CID와 교차시킵니다. 후보가 많으면 표시 범위를 제한하고 취소·페이지 처리와 캐시를 적용하여 한 글자 입력마다 모든 후보를 DB 조회하지 않게 합니다.

통신 없이 즉시 가능한 범위는 자동완성, 보유 이름·번호 검색, 이미 연결된 CID의 다국어 묶기입니다. 처음 접한 외국어 이름과 보유 CID의 연결은 DB 응답을 기다립니다. 전역 CID 목록을 없애는 데 따른 이 차이를 구현과 검증에서 명확하게 유지합니다.

## 7. cardNames.json 유지와 인덱스 제거

`public/cardNames.json`의 계약은 유지합니다.

```json
{ "names": ["예시 카드"], "numbers": ["TEST-KR001"], "updatedAt": 1788390000000 }
```

- 경로·배열 형식·기존 목록 동기화 역할을 유지합니다. `cidIndex.json`은 새로 만들지 않습니다.
- 생성 원천만 세 인덱스에서 `cards.names`·`cards.numbers`로 변경합니다.
- 목록에는 카드별 연결 정보가 없으므로, 단순 증분 삭제는 다른 카드가 공유하는 이름을 지울 수 있습니다. 기존 변경 대기열을 갱신 신호로 사용하되 목록 생성은 필요한 필드만 페이지 조회하여 전체 집합을 다시 만듭니다.
- 동시에 발생한 변경을 묶어 한 번 재생성합니다. 대기 100개마다 전체 DB를 반복 스캔하지 않도록 작업을 합칩니다.
- 시작 시 확보한 대기 기록의 버전만 완료 처리하고, 생성 중 추가된 변경은 후속 작업으로 남깁니다. 변경 유실 방지용 잠금·조건부 저장·실패 복구를 유지합니다.
- 원본 저장 후 카드 검색은 즉시 DB에서 가능하고, 자동완성 목록은 목록 갱신 완료 시 반영됩니다.
- 별도 서버 `suggestCardNames`의 접두사 추천은 `cardNames.json`의 이름 목록을 사용합니다.
- `getInitialData`에서 `idx_cid.json`을 읽어 응답에 합치는 경로를 최종 제거합니다. 이름·번호 목록 동기화는 그대로 유지합니다.
- 클라이언트의 구형 `cidIndex` 캐시는 새 클라이언트에서 사용하지 않으며, 새 데이터 적용이 성공한 뒤 정리합니다. 인벤토리·팩·레어도 캐시를 함께 지우지 않습니다.

## 8. 구현 범위와 순서

| 순서 | 변경 영역 | 내용 |
|---|---|---|
| 1 | 공통 카드 조회 서비스 | 이름·번호·CID 조회, 문서 캐시, CID 확인 규칙 |
| 2 | `inventoryStorage` 및 새 `inventoryMigrationService` | v2 생성, 로드 시 이관, 부분 진행, 조건부 저장 |
| 3 | `routes/user.js` | 자동 v2 전환, 보유 내역 선표시, 버전·진행 상태·CID 응답 |
| 4 | `routes/card.js`, `routes/migration.js` | 신규 등록과 이동·차감·외부 이관에서 CID 유지 |
| 5 | `public/script.js` | 7열 호환, 부분 갱신, 검색 결과 캐시, CID별 보유 검색 |
| 6 | 카드 검색 API와 번호 보정 | JSON 조회 분기 제거, 원본 문서 응답으로 통일 |

기존 작업의 대기열·잠금·배포 함수 식별자는 전환 중 공유하여 예약된 작업을 잃지 않게 합니다. 운영 ID 이름만을 위한 별도 DB 이관은 하지 않습니다.

## 9. 전환과 구형 클라이언트

1. 사용자 로컬 확인 후 백엔드에 v2 호환과 DB 검색을 먼저 반영합니다.
2. `cardNames.json`을 DB 원천으로 생성하고 새 프론트엔드를 배포합니다.
3. 사용자는 인벤토리 로드 시 자동 이관됩니다. 전체 사용자 인벤토리를 일괄 수정하는 작업은 수행하지 않습니다.
4. 구형 클라이언트의 CID 없는 쓰기도 새 서버에서 보완하여 v2 데이터를 보존합니다.
5. 구형 탭의 전역 CID 의존은 한시적 호환 응답으로 유지합니다. 필요 시 전환 기간에만 기존 CID 파일을 유지하고, 새 클라이언트는 읽지 않습니다.
6. 구형 탭·함수 호출 전환 확인 후 옛 CID 응답과 인덱스 파일 생성·조회·운영 파일을 정리합니다. 최종 상태에서는 세 인덱스 JSON에 의존하지 않습니다.

운영 배포와 구형 파일 삭제는 사용자 실행 절차로 안내합니다. v2 저장 후 구형 백엔드로 롤백하면 CID를 유실할 수 있으므로, 롤백 대상에도 v2 필드 보존과 조건부 쓰기가 있어야 합니다.

## 10. 사용자 검증 및 완료 기준

프로젝트 `.clinerules`에 따라 자동 테스트 실행 대신 다음 사용자 검증 절차를 제공합니다. 구현 승인 후에도 별도 요청 전에는 커밋·푸시·배포·운영 이관을 실행하지 않습니다.

| 확인 항목 | 기대 결과 |
|---|---|
| v1 인벤토리 최초 로드 | 번호별 CID 자동 확보 후 서버 파일이 v2로 저장 |
| CID가 전부 확인된 v2 재로드 | 이관용 전체 DB 조회가 다시 발생하지 않음 |
| 큰 v1 인벤토리 | 먼저 재고 표시, 묶음별 진행 저장과 자동 후속 처리 |
| 없는 번호·모호한 이름 | 보유 내역 보존, 임의 CID 없이 null 및 미확정 수 표시 |
| DB/Storage 일시 오류 | 실패를 완료로 표시하지 않고 이후 재시도 |
| 이관 중 다른 탭에서 추가·이동·차감 | 수량·위치·새 항목 유실 없이 최종 CID와 버전 일치 |
| 신규 등록 및 기존 6열 이관 | CID를 포함한 v2 저장, 기존 사용자 입력 형식 유지 |
| 미확정 카드가 나중에 DB에 생성됨 | 재시도 간격 이후 CID 자동 보완 |
| 검색 응답 후 다른 입력 행에서 같은 카드 검색 | 유효 캐시 내에서는 서버 요청 없이 번호·레어도 표시 |
| 한국어 검색으로 일본어·영어 보유 내역 조회 | 같은 CID의 모든 언어 항목 표시 및 중복 없는 합계 |
| 부분 일치/초성 검색 | 로컬 후보 즉시 표시, 필요한 다국어 확장만 후속 조회 |
| CID 미확정·구형 로컬 캐시 | 재고 사라짐 없이 이름·번호 검색 유지 |
| 번호 보정·공식 링크·CID URL·종류 라벨 | DB·저장된 CID·문서 캐시로 정상 처리 |
| 원본 카드 변경·삭제·동시 수집 | cardNames의 이름·번호 갱신과 대기 기록 보존 |
| 최종 구형 파일 제거 | 세 idx 파일 없이 검색·등록·자동완성·재고 동작 |

최종 완료 기준은 인덱스 세 파일 없이 DB 조회와 검색 캐시가 작동하고, cardNames 자동완성 형식이 유지되며, v1 인벤토리의 자동 전환과 CID 기반 다국어 보유카드 검색이 연결된 상태입니다. 미확정 데이터는 분리하여 보고하고 보유 수량을 손실 없이 유지해야 합니다.
