# 인벤토리 v2 및 DB 검색 전환 확인

작성일: 2026-09-03. 코드는 반영했으며 자동 테스트·구문 검사·브라우저 실행·운영 배포는 실행하지 않았습니다. 프로젝트 지침에 따라 사용자가 아래 항목을 직접 확인합니다.

## 반영한 동작

- 이름·번호·CID 검색은 `cards` 원본과 60초 서버 문서 캐시를 사용합니다. 종류 메타데이터는 최대 100개 문서씩 묶어서 읽습니다.
- `cardNames.json`은 기존 `{ names, numbers, updatedAt }` 형식입니다. 생성 시 원본의 두 배열만 500개 문서씩 읽어 전체 합집합을 저장합니다.
- 기존 변경 대기열·잠금·Tasks는 목록 갱신용으로 유지합니다. 시작 시점의 대기 기록을 묶어서 목록을 한 번 생성하고, 새 버전의 변경은 후속 처리합니다.
- 신규 인벤토리는 v2입니다. 기존 v1은 로드/수정 시 한 번에 최대 40개 번호의 CID를 확보합니다. 한 묶음의 조회 시간은 약 12초로 제한하며, 미처리 데이터는 다음 요청에서 이어갑니다.
- CID는 `cards[수록번호].cid`에 문자열 또는 `null`로 저장합니다. `cidCheckedAt`은 해당 연결을 마지막으로 확인한 시각입니다.
- 남은 미처리 항목이 있으면 version 1, 정상적으로 확인했으나 미발견인 null 항목만 남았다면 version 2입니다. null 항목은 24시간 후 로드 시 재확인합니다.
- DB 오류는 `cidMigration.retryableError`와 재시도 시각을 기록합니다. 클라이언트는 30초 이상 간격으로 재시도하며 반복 오류 때 간격을 늘립니다.
- 클라이언트 후속 로드는 CID만 적용하여 그 사이 사용자가 변경한 수량을 보존합니다. 탭이 보이지 않거나 다른 계정으로 전환되면 해당 후속 작업을 중단/보류합니다.
- 등록 페이지의 이름·번호 검색 결과는 입력 행을 넘어 60초간 캐시합니다. 동시에 같은 요청이 들어오면 진행 중 요청을 공유합니다.
- 인벤토리 응답은 기존 6열 끝에 CID를 붙인 7열입니다. 기존 6열 시트 입력과 구형 클라이언트 등록 요청은 서버에서 CID를 보완합니다.

## 로컬 확인 준비

1. 로컬 Functions·Firestore·Storage가 연결된 환경에서 백엔드와 프론트엔드를 다시 시작합니다. 운영 데이터 대신 로컬 카드 문서와 인벤토리 사본을 사용합니다.
2. 동일 CID의 한국어·일본어 이름과 번호가 포함된 `cards` 문서, 다른 CID의 카드 문서를 준비합니다. 각 문서에 `names`, `numbers`, `info`가 있어야 합니다.
3. 해당 번호의 보유 내역을 서로 다른 위치·레어도·수량으로 만든 version 1 인벤토리를 준비합니다. 이관 전 수량·집계를 기록합니다.

## v1 → v2 자동 이관

1. 로그인 후 보유카드 목록을 로드합니다.
2. Storage에서 인벤토리의 `version: 2`, 번호별 `cid`, `cidCheckedAt`을 확인합니다.
3. 이름·번호·레어도·위치·일러스트·수량과 전체 집계가 이관 전과 같은지 비교합니다.
4. 다시 로드하여 CID가 모두 있는 v2는 이관용 이름·번호 쿼리를 반복하지 않는지 확인합니다. 일반 상세 검색에 필요한 조회는 별개입니다.
5. 40개를 넘는 번호로 반복합니다. 응답의 `inventoryMigration.pendingCount`가 줄고 마지막에 version 2가 되는지 확인합니다.
6. DB에 없는 번호, 이름과 번호가 충돌하는 항목은 `cid: null`로 남고 재고가 삭제되지 않아야 합니다. 응답의 `unresolvedCount`로 확인할 수 있습니다.

## 실패와 동시 작업

- 로컬 DB 접근 실패 중 로드하면 기존 재고가 표시되고 전환 완료로 잘못 보고하지 않아야 합니다.
- 이관 중 다른 탭에서 수량 추가·이동·차감을 수행합니다. 최신 수량과 위치가 보존되고 CID만 추가되는지 확인합니다.
- 이관 중 카드를 삭제하면 후속 저장이 그 카드를 되살리지 않아야 합니다.
- 새 카드를 동시에 추가하면 그 항목의 CID도 검증되거나 미처리 상태로 남아 후속 처리되어야 합니다.
- 미확정 번호를 DB에 추가한 뒤, 로컬 사본의 `cidCheckedAt`을 24시간 이전으로 설정하고 재로드하여 자동 연결되는지 확인합니다.
- 지원하지 않는 미래 버전의 로컬 인벤토리는 덮어쓰지 않아야 합니다.

Storage 에뮬레이터는 운영의 generation 조건부 업로드 충돌을 완전히 재현하지 못할 수 있습니다. 동시에 탭을 사용한 확인만으로 모든 충돌 방어가 검증된 것으로 보지 않습니다.

## 등록과 캐시

- 새 이름 검색 시 응답에 CID·번호별 레어도·일러스트·언어 정보가 포함되는지 확인합니다.
- 다른 입력 행에서 같은 이름을 60초 안에 조회하면 이름 검색 API가 다시 나가지 않는지 브라우저 Network에서 확인합니다. 브라우저 자체 HTTP 캐시도 별도로 작동할 수 있습니다.
- 같은 카드의 번호를 바꿀 때 기존 `dataset.cardData`의 번호별 레어도를 즉시 재사용하는지 확인합니다.
- 번호로 시작한 검색은 그 번호의 언어에 맞는 이름과 번호 목록을 표시해야 합니다.
- 등록 후 Storage와 응답 모두 CID를 포함해야 합니다. 이동·차감·시트/데이터 이관 후에도 CID가 유지되어야 합니다.
- 모바일/데스크톱 전환, 입력 행 복제·복원, 기존 시트 이관에서 CID가 일반 입력 열로 노출되지 않는지 확인합니다.

## 다국어 보유카드 검색

- 한국어 이름으로 검색했을 때 같은 CID의 일본어·영어 번호도 보유 결과에 포함되고 수량이 중복 합산되지 않아야 합니다.
- 보유 항목의 CID를 이미 알고 있으면 로컬 재고를 먼저 표시합니다. 처음 접하는 외국어 이름은 DB 조회 후 연결합니다.
- 부분 일치·초성 검색은 기존 로컬 결과를 먼저 표시하고 40개 후보 이름씩 다국어 보유 내역을 확장합니다. 남은 후보는 “다른 언어의 보유카드 더 찾기”로 이어집니다.
- 검색 확장 중 다른 검색이나 상세 화면으로 이동했을 때 이전 요청이 새 화면을 덮어쓰지 않아야 합니다.
- CID가 없는 기존 항목은 이름·번호 일치 검색에서 계속 보여야 합니다.
- CID URL 직접 진입, 공식 상세 링크, 종류 라벨, 기존 JP→KR 번호 보정을 확인합니다.

## 목록 생성과 배포 전환

1. 관리자 `POST /rebuildCardNames`로 목록을 원본 DB에서 재생성합니다. 재생성 HTTP 진입점은 `/rebuildCardNames`로 통일했습니다. 기존 `/rebuildAllCardIndexes`, `/buildIndex`, `/syncCardManifestToStorage` 별칭은 코드에서 제거했습니다. 운영의 구형 함수는 새 함수 배포 성공 후 삭제 여부를 확인합니다.
2. 새 `cardNames.json`의 이름·번호 목록을 확인합니다. 기존 세 idx 파일을 로컬에서 사용 불가능하게 해도 새 검색·목록 생성이 동작해야 합니다.
3. 카드 수집 후 목록 갱신과 대기 기록 처리를 확인합니다. 공유하는 이름은 한 카드가 삭제되어도 다른 카드가 남아 있으면 목록에 유지되어야 합니다.
4. 후속 갱신 실행에는 기존 Tasks 에뮬레이터가 필요합니다. 작업 중 추가된 변경과 저장 실패 시 대기 기록 보존을 확인합니다.
5. 사용자 로컬 확인 후 백엔드 → 목록 재생성 → 프론트엔드 순서로 GitHub 배포합니다.
6. 새 클라이언트는 `getInitialData`에 `inventorySchema: 2`를 보냅니다. 구형 탭에는 전환 기간 동안 DB에서 만든 `cids`를 응답에 포함합니다. 이 호환 경로도 idx JSON은 읽지 않습니다.
7. 운영의 구형 idx 파일은 코드에서 사용하지 않지만 이번 작업에서 물리적으로 삭제하지 않았습니다. 배포 확인 후 사용자가 정리합니다.

## 검증 정의

기존 목록 관련 테스트 정의를 새 형식에 맞추고 `functions/test/inventoryV2.test.js`를 추가했습니다. v2 전환·미발견·오류·동시 수량 변경·삭제·추가 재시도·큰 인벤토리 진행 저장을 격리된 대역으로 확인합니다. 최초 구현 시에는 실행하지 않았으며, 2026-09-03 사용자의 문제 확인 요청에 따라 실행했습니다. 클라이언트 회귀 테스트 3개를 포함한 전체 29개가 통과했습니다(Node.js 25.6.0). 변경 JavaScript 구문 검사와 `git diff --check`도 통과했습니다.

추가 점검에서 늦게 도착한 CID 조회가 새 검색을 덮어쓸 수 있는 경로를 차단했습니다. 이관 조회가 `success: false`를 반환하면 재시도하고, 조회 중 계정이 바뀌면 이전 계정의 오류로 재시도를 예약하지 않도록 수정했습니다. `functions/test/inventoryClient.test.js`에서 이 세 상황을 격리 검증합니다.

운영 성능·실제 브라우저·Node.js 24 실행·실제 Storage 충돌은 사용자 확인이 남아 있습니다.

## 사용자 실행 중 발견한 FieldPath 오류 수정

목록 생성의 `admin.firestore.FieldPath.documentId()`에서 FieldPath가 undefined인 오류가 보고되었습니다. 설치된 SDK의 `firebase-admin/firestore`에서 FieldPath를 직접 가져와 공통 설정으로 내보내도록 수정했습니다. 같은 호출이 있던 번호 이관 서비스와 관련 테스트 대역도 변경했습니다.

로컬 Functions를 다시 시작한 뒤 같은 번호 검색 또는 관리자 목록 재생성을 다시 실행하여 오류 해소를 확인합니다. 이 오류는 카드 원본 저장 이후 목록 생성에서 발생하므로, 원본과 남은 갱신 대기 기록을 삭제하지 않습니다. 이후 격리 테스트는 통과했지만 실제 Functions의 목록 재생성 경로 확인은 남아 있습니다.
